## 5–6. Hierarchy and relation semantics

Hierarchies contain typed IDs, multiple roots, ordered node maps, explicit edges, revision, and timestamps. Nodes carry artifact reference, scope, maturity, freshness, activation, and provenance. Shared children are allowed.

- Specializes: narrower/equal eligible child becomes Primary; parent becomes SupportingContext.
- Refines: both remain applied; child becomes Refinement.
- Excepts: eligible evidence-backed child suppresses the explicitly linked parent directive and receives Exception role.
- Supersedes: old parent points to new child; explicit scoped replacement only. Chains record the final live suppressor.
- DependsOn: prerequisite parent points to dependent child; health propagation without inheritance precedence.

## 7–9. Scope, applicability, and scope relations

Scopes conjunct Equals, NotEquals, In, Exists, Bool, inclusive IntegerRange, semver VersionRange, and Custom predicates over typed String/Integer/Boolean/Version values. Canonical context-key constants are provided. Context accepts both typed library JSON and ordinary CLI primitive objects.

All true means Applicable; any false means Inapplicable; true plus unknown means PartiallyKnown; all unknown means Unknown. Empty scope is universal. Missing keys never match, including Exists/NotEquals. Custom evaluators are not registered in this pass and remain Unknown.

Scope comparison normalizes finite sets, exclusions, integer intervals, and stable-release semver intervals by dimension. It proves containment, disjointness, or overlap; unsupported combinations remain Unknown. Prerelease relationships are conservative. Specificity is a lexicographic tuple of distinct exact, bounded, and existence dimensions, never a public float or arbitrary winner rule.

## 10–11. Validation and artifact compatibility

Validation rejects self-reference, missing nodes/roots, duplicate edges, mismatched node identities, malformed empty artifact references/revisions, invalid root membership, specialization/mixed precedence cycles, supersession cycles, invalid specialization/exception scopes, and cross-kind precedence. Unknown scope comparison warns and cannot establish an override. Health-dependency cycles warn and fail closed during eligibility.

Concrete precedence requires matching kinds. Abstract references map to their compatible concrete family. DependsOn permits cross-kind relationships, including Recovery and CausalMechanism.

## 12–19. Resolution behavior

Resolution validates first, evaluates scopes, checks lifecycle, propagates dependency health, constructs eligible precedence, handles supersession/exceptions/specialization/refinement, records conflicts, and materializes deterministic output. Ordered incoming/outgoing indexes avoid per-node scans of all edges.

Specializations retain parents as supporting context. Refinements compose. Exceptions require Active, Fresh, sufficiently mature, non-contradicted, evidence-backed nodes and a validated relationship. Stale/candidate knowledge can be separately advisory; quarantined and disabled knowledge cannot override. Unknown applicability preserves known defaults. Explicit supersession suppresses old knowledge only in matching context.

Competing eligible sibling specializations/exceptions/replacements raise explicit conflicts and keep the default parent; alternatives are SupportingContext. Sibling refinements compose. Conflict detection precedes mutations within each phase, including multi-parent cases. No creation-time or ID tie breaker chooses authority.

## 20. Resolution trace

Trace entries contain contiguous `sequence`, `node`, `action`, and `reason`. They expose candidate discovery, applicability, lifecycle rejection, application roles, suppression, supersession, and conflict. Output uses stable node/edge ordering, canonical predicate order, and deterministic lineage. Resolution generates no random IDs or current timestamps.

## 21. CLI

Added functional commands:

```text
hardknock knowledge hierarchy show
hardknock knowledge hierarchy validate
hardknock knowledge hierarchy import <file>
hardknock knowledge resolve --context <file>
hardknock knowledge explain --context <file>
```

`--hierarchy <file>` reads an explicit hierarchy; `--id` selects a stored one. All commands support `--json`, with schema_version 1 in the existing response envelope. Resolve/explain accept optional policy JSON. Human output includes roles, suppression reasons, unknown knowledge, conflicts, and explanation trace.

## 26–27. Known limitations, deviations, and rationale

- Artifact IDs and evidence IDs remain references to caller-owned catalogs. Callers supply assessed node health; Pass 1 does not fetch every external artifact or recalculate evidence sufficiency from raw observations.
- Existing V0.17 relations have explicit projection adapters, not automatic live synchronization. Old exceptions lack independent lifecycle; callers must provide an assessed child rather than silently promoting them.
- SQLite stores one atomic hierarchy aggregate instead of three denormalized tables, preserving one representation. No resolution history is stored.
- A node is an atomic directive for suppression. Partial artifact suppression requires separate directive nodes and explicit edges.
- The minimal conflict detector conservatively reports structural competitors. It does not understand contradictory prose, inspect arbitrary payloads, or detect semantic conflicts across independent roots. Sibling refinements compose by their explicit additive relation.
- Prerelease scope containment and custom/set/absence predicates can remain Unknown. This preserves safe fallback.
- `stale_exception_can_override=true` is rejected rather than weakening the mandatory freshness boundary. Advisory knowledge has a separate collection.
- Exceptions require contained scopes, a stricter conservative interpretation than overlap alone. Equal-scope explicit exceptions remain permitted.
- Shared descendants make the model a rooted DAG rather than a strict single-parent forest; this allows a directive to explicitly suppress multiple conflicting parents.
- Dense/deep graphs can produce inherently large ancestor-lineage output. The scaling fixture uses moderate four-way branching; no large benchmark suite was added.
- No commits were created; changes remain available for review in the working tree.
